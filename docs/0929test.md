## 0. 本日结论（TL;DR）

3. 同段代码还有一个同类隐患（读未初始化数组），且它会被"环境状态联动"方案踩到：**已一并加守卫 + 清零兜底**。

**B = `concentration_number`**（每格粒子数）。

## 2. 排查过程

### 2.1 读点清单（先把"谁读谁写"钉死）

用逐字节检索（`grep -r` 在本仓会漏匹配，改用 Python 逐行扫）得到：

- `init_bin_mass`：写 `:129`（分配）、`:141-142`（**仅 Tag_init=1** 时从配置读入）；读 `:577`（组装 `binx_mass`）、
  `:618/:620/:640/:642`（都在 `Tag_init=1` 分支内）、`:661`（`Tag_init=1`，单列）、`:674`（**块④，无 Tag_init 条件**）。
- `init_bin_number`：写 `:131`（分配）、`:149`（**仅 nucl_model≠5** 时读入）；读 `:619/:641/:664`（都在 nucl_model≠5 分支内）、
  `:675`（**块④**）。
- 结论：**只有块④（`:674/:675`）会在数组未赋值时读它们**；`:577` 的 `binx_mass` 虽然也读，但其消费者
  `:620/:642` 都在 `Tag_init=1` 分支内，`Tag_init=0` 时算出来没人用（今天无害，属"踩线未触发"）。

### 2.2 数组 A → B 是否需要"倒推"

用离线脚本照抄 `dist_init_mass_number`（`N_sizebin ≤ 200` 分支）与档平均直径公式，比较
"内置数分布精确积分"与"用档几何均径从质量倒推"：

| 档 | 倒推 / 精确 |
|---|---|
| 1 | 4.323 |
| 2 | 3.920 |
| 3 | 5.105 |
| 4 | 1.366 |
| 5 | 0.458 |
| 6 | 1.037 |
| 7 | 0.620 |
| **合计** | **2.222** |

**结论：不采用倒推**。它不是模型自身口径的逆运算（内核自己注释掉的 "有效直径" 关系也说明二者不等），
会把论文案例的初值改成另一套；而且该模式并不缺粒子数 —— `number_init(k)` 已经在 `:462` 算好并在使用。

### 2.3 黑碳判据：命中列数与倍数（离线复刻验证）

复刻 `FracDiscretization` 的组合枚举（5 个族；边界取配置里的手写值 0/0.2/0.8/1）：

| 组成档段数 | 网格总列数 | 旧判据（第1族下限=0） | 新判据（第4族上限=1） | 对照：硫酸盐判据（第1族上限=1） | 初始总质量倍数 |
|---|---|---|---|---|---|
| 3 | 20 | **11 列** | **1 列（f=3）** | 1 列（f=20） | 6.0000 → **1.0000** |
| 5 | 70 | **35 列** | **1 列** | 1 列 | 18.0000 → **1.0000** |

- 倍数公式 `(1+M)/2` 精确复现实测的 6.0000（3 段）与 18.0000（5 段）。
- 交叉验证：复刻出 5 个"占满列"（第5族→f=1、第4族/黑碳→f=3、第3族→f=6、第2族→f=11、第1族→f=20），
  与既有审查里从真实运行 dump 观测到的 5 个非零列完全一致 ⇒ 复刻可信。

### 2.4 顺带核查：重分配会不会把这两列搬走

复刻 `redistribution_fraction` 的"归属列"判定（区间下界为 0 时闭、非 0 时左开右闭；命中后源格清零但循环不 break）：

- 修正后：纯硫酸盐格（f=20）与纯黑碳格（f=3）**都是该子程序的不动点** ⇒ 重分配无副作用，不需要改它。
- 修正前：11 列里各半份的黑碳会**全部叠到 f=3 一列** ⇒ 质量与粒子数各自 ×11 且彼此自洽
  ⇒ **不触发一致性体检** ⇒ 这就是"能跑完但初值虚高 6 倍"的静默机制。

### 2.5 为什么隐患至今没炸

- 发布的 Windows 运行核是旧构建（无一致性体检），读到未初始化值只静默出错；
- 刚分配的内存常恰好为 0，所以 `Tag_init=0` 那条路看起来"正常"；
- 而未初始化的**粒子数**在 `nucl_model=5` 的外混臂会把"有质量、粒子数为 0"的格子暴露给体检 ⇒ 才被发现。

### 2.6 用旧核跑出的真实"改前"基线（本机实测，2026-09-29）

用仓库里已提交的 Windows 运行核（1.1）在**临时目录**里把 7 个 case 跑了一遍（未污染仓库；
临时目录 2.9 GB 已删，只留 139 KB 的 `report.txt`/`mass_init.txt`/`run.log` 夹具在 `/tmp/pre0929_fixture`）：

| case | 初始总质量（旧核实测） | 说明 |
|---|---|---|
| T1 `nl=5` 内混 | `37.679073599845388` | 与 0921 审查记录的内混臂一致 |
| T2 `nl=5` 外混 + 内混初值 | `228.81807486240999` | = 内混值被问题 2 的写入污染（见下） |
| T3 `nl=5` 外混 + 外混初值 | `226.07444159907240` | = **6.0000 × T1** |
| T4 / T6 | `21.583170063260344` | = 配置文件 30 物种总量，应保持不变 |
| T5 `Tag_init=0` 外混 | `14.464046851670814` | 比 T7 少 `4.26466` |
| T7 `Tag_init=0` 内混 | `18.728707753710463` | T5 的对照臂 |

四条结论：

1. **11 列机制得到真实数据印证**：T3 的黑碳 = `207.2349 = 11 × 18.8395`（18.8395 = 内混臂总量的一半），
   硫酸盐 = `18.8395`（1 列）⇒ 与离线复刻的"命中 11 列 / 6 倍"完全一致。
2. **更正一处先前判断**：`nl=5` 且 `Tag_init=1`（出厂雾霾模板正是这种）时，`init_bin_mass` **是有值的**
   —— 该行会被读入（`:137-147` 只按 `Tag_init` 分支，不看 `nucl_model`），未定义的只有 `init_bin_number`。
   所以 T2 = 228.82 = hazy 初值 **叠加** 配置文件的逐档质量，而不是"两个数组都是垃圾"。已回改
   `docs/0929check.md` 的对应表格。
3. **新发现（A6 的由来）**：`Tag_init=0` + `N_frac>1` 时块④ 覆盖第 1 列，把**第 5 族（矿物尘/`MD`）**的质量
   啃掉：T5 里它是 `1.007854978e-311`（次正规数 = 未初始化内存），T7 里是 `4.264660902`，差正是 `4.26466`。
   其余 29 个物种两臂逐位相同 ⇒ 修复后 T5 应精确等于 T7（这就是 A6）。
4. **T7 在旧核上初始化后异常退出**（日志停在 init 阶段、无 Fortran 报错）；"只开冷凝"的变体则把自适应步长
   塌缩到几乎走不动（日志 9 万多行才到 53%）。其初值写在 `report.txt` 里、与是否跑完无关，故 A6 照常可用；
   但已在 `0929linux.md` 注明：T7 的退出码只作观察记录，不作为失败判据。

顺带把这一批断言做成了可执行判定：`scripts/check_init_fix_linux.py`（跑 7 个 case → 核对 A1–A6 →
输出 `install_logs/20260929_runs/result.json`，退出码 0 = 全过）。已用上表的"改前"数据自测：
A1/A2/A3/A6 全部 FAIL（含 T3 的 6 倍与 T5 少 4.2647），A4 PASS（旧核无体检）⇒ 判据有区分力。
