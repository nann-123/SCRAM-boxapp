## 三、修改过程中撞到并修掉的三个坑（记录，避免重犯）

这三个都不是原始缺陷，是**本轮改动自己引入或暴露的**，所以特别记下来。

### 坑 1：PowerShell 脚本里不能写中文（否则语法会被悄悄吃掉）

我给 `scripts/make_windows_devkit.ps1` 加中文注释后，重新打包发现清单里
`Excluded runtime directories:` **后面是空的**。排查结论：

- Windows PowerShell 5.1 读取**无 BOM** 的 `.ps1` 时按 **ANSI（cp936）** 解码；
- 该文件是 UTF-8 无 BOM，中文注释的字节在 GBK 下解出乱码，
  **乱码尾字节把行尾换行符吃掉了** ⇒ 下一行 `$RuntimeExcludeDirs = @(...)` 被并进注释；
- 于是该变量从未被赋值 ⇒ 打包时 **`/XD` 排除项整个失效**（等于没排除任何目录）。

**处置**：把注释改回纯 ASCII，并加了一条"这个文件必须保持纯 ASCII"的提示。
**验证**：临时造一个 `source\SCRAM1.1\junk_marker.txt` 探针，重打包后清单里探针命中 **0 次**，
且排除项列表正常打印。
**约定**：本仓库 `.ps1` 一律 ASCII（另外两个 `.ps1` 本来就是 ASCII）——这条也适用于后续维护。

### 坑 2：检查脚本因为"打印"而崩掉

`scripts/check_runtime_version.py` 里用了 `⇒`（U+21D2，**不在 GBK 字符集内**）。
直接跑没问题，但**被重定向/管道时** stdout 变成 GBK，`print` 抛
`UnicodeEncodeError`，脚本以一个和内核版本毫无关系的错误退出。
`run_standard_tests.py` 拿到非 0/非 3 的退出码，还会误报成"找不到任何 ProgramSCRAM"。

**处置**：① 把 `⇒` 等换成 ASCII；② 脚本开头加
`sys.stdout.reconfigure(errors="replace")` 兜底；③ 标准测试里对未知退出码给出
"自检脚本未能给出结论（退出码 N）"的准确提示。
**验证**：在管道（GBK）场景下复测，正常输出结论，退出码 3。

**顺带发现：同类问题也存在于一个既有脚本**。`scripts/check_field_registry.py` 会打印 `✅` / `⚠`，
这两个字符**不在 GBK 字符集内**；直接跑没事（终端是 UTF-8），但**一旦被管道或重定向**就抛
`UnicodeEncodeError` 并以退出码 1 结束 —— 会让人误以为"字段对账发现了严重问题"。
已一并加上同样的 `reconfigure(errors="replace")` 兜底。
（影响面：所有会输出 `✅`/`⚠`/`⇒` 且可能在 CI/流水线里被重定向的检查脚本）

### 坑 3：`argparse` 的参数名不能带点

`--require-core-1.2` 会让 argparse 生成属性名 `require_core_1.2`，`args.require_core_1_2`
直接 `AttributeError`。**处置**：显式 `dest="require_core_12"`。
