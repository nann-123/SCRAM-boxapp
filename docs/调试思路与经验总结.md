## 一、这段调试到底在调什么

先说清性质，否则容易把三类完全不同的东西混在一起打：

| 类别 | 含义 | 本项目里的例子 | 该不该动代码 |
|---|---|---|---|
| **移植层缺陷**（`port`） | 后加的界面/包装层写错了 | #11 预设覆盖用户设置、#12 死控件、#19 `explicit_keys` 丢失、#24 越界死循环 | ✅ 该修，计入发布闸门 |
| **本体实现错误**（`upstream-defect`） | 2015 年那份代码本身的逻辑错 | #9 读配置指针错位、#7 重分配重复交付 | ⚠️ 要修就得改核心 + 重编译 |
| **模型未定义域**（`undefined-domain`） | 输入状态在模型语义里从没定义过 | #2 / #5 / #13（"质量为 0 但粒子数不为 0"） | ❌ 不该改核心；在界面层挡住即可 |
| **有意为之**（`by-design`） | 作者为特定场景的决定 | #14 方法 3/5 粒子数暴涨、#17 排放窗口 44 分钟 | ❌ 不用改；要做成可配属新功能 |

**这段调试的主战场是"移植层"** —— 也就是回答一个问题：

> **用户能点、能配的东西，核心到底认不认？**

## 三、几个重要缺陷的完整破案过程

### #9 读配置指针错位：先为复现论文案例，反而撞上崩溃

**怎么发现的**：我们要复现论文第 3 节的"雾霾天冷凝验证"案例。该案例需要一个恒定硫酸盐源，而代码把它硬编码在 `nucl_model=5` 分支里。按论文口径设成 5 之后，程序**连配置都读不过去**，直接崩。

**怎么定位的**：
1. **最小复现**：把崩溃缩到"标准 56 行配置 + `nucl_model=5`"这一条
2. **读代码找差异**：`ModuleDiscretization.f90:129-136` 在 `nucl_model=5` 时**跳过了 3 行读取却没有消费它们**；Fortran 的顺序读按行推进指针，跳过不等于消费 ⇒ 后续读粒径边界时读到了错误的数据行
3. **对照验证**：手工删掉那 3 行（53 行版本）就能跑 ⇒ 反证了"指针错位"的判断

**怎么解决的**：改成**无条件读入**那 3 行（对 `nucl_model≠5` 与原代码完全等价；对 `=5` 读入但不使用，只让指针到位）。

**怎么确认没改坏**：跑通后初始总质量 `226.07444159907240`，与 7 月的记录一致 ⇒ 物理结果未变。同时 53 行的旧绕过办法反而报错，证明修复正确。

**卡了多久**：修复 2026-09-11 就进了源码树，但**Windows 的 exe 至今没重编译** ⇒ 用户手里那个崩溃依然存在。**这是本项目最贵的一课**（见经验 ⑪）。

### #7 重分配数量不守恒：三次失败补丁换一次正确诊断

**怎么发现的**：教学模板「雾霾天 凝并 + 冷凝」跑标准测试 `failed`，日志里有一句法文 `non conservation du nombre total !!`（总粒子数不守恒）。

**关键的第一步：先分清"谁的错"** —— 把**同一份配置（只改第 7 行方法号）交给原版程序**跑，结果症状一模一样 ⇒ 确认是本体行为，不是我们封装引入的。

**然后走了三段弯路（这是最值得记的部分）**：

| 阶段 | 做法 | 结果 | 教训 |
|---|---|---|---|
| v1/v2/v3 | 给 `euler_coupled.f90` 里几个除法加"分母保护" | **全部无效**，结果与原版**逐位相同** | guard 条件在该相位**恒为假** ⇒ "改了没变化"是必然而非证据。**先证明条件可达，再写补丁** |
| 人工复核 | 用 `-ffpe-trap=zero,invalid,overflow` 重编译 + 加 `-fbacktrace` | 首个浮点异常直接指出 `ModuleThermodynamics.f90:264`（`log10(0)`） | **浮点类问题必须先拿到"文件:行号"再谈补丁** |
| 加保护后复跑 | 异常落到 `euler_coupled.f90:244`；再插桩打印 | 发现真因：**交付时累加器按目标段索引、交付循环按源段迭代**，同一相位多个源落到同一目标 ⇒ **同一份量被交付多次**，数量净增 0.054% → 触发停机 | 定位靠插桩，不靠猜 |

**怎么解决的**：产出 `proposals/bug7_double_add_v4.patch`。打过补丁的版本：`failed → ok`，跑满 512 步**精确守恒、0 次触发停机**（原版同配置触发 8 次并停机）。

**产品侧处置**：不改核心，把教学模板默认方法从 6 改回 2（论文口径），从根上绕开。

**顺带纠正了两个误判**：① 早先以为"除零在 `euler_coupled` 的循环内"，三次补丁证明不是；② 早先记为 9.77e-6 的"残差"其实是**交付前的中间量**（按 `AN/BN+CN/DN≡1` 恒等于送出比例），不是守恒残差 —— 拿它当证据会得出完全相反的结论。

### #10 截图全是方框：原假设错了，而且"永远修不好"

**怎么发现的**：手册和 README 里的界面截图文字全是"□□□□"。台账当时的判断是"生成机器缺中文字体，去有字体的 Windows 重生成即可"。

**怎么定位根因（本次）**：先做最直接的检查 —— **这台 Windows 的 `C:\Windows\Fonts` 里明明有 `msyh.ttc`（微软雅黑）**，但 Qt 报 **0 个字体家族**。于是做**同机对照实验**：

| 平台插件 | Qt 能看到的字体家族 |
|---|---|
| `offscreen`（脚本强制的） | **0 个** |
| `windows`（真实平台） | **140 个**，含脚本要的 `Microsoft YaHei UI` |

⇒ **根因是脚本第一行写死的 `QT_QPA_PLATFORM=offscreen`**，而 Qt 的 offscreen 插件在 Windows 上不加载系统字体库。**这解释了为什么"去 Windows 重生成"永远不成功 —— 换任何 Windows 机器都一样。**

**怎么解决的**：平台自适应（Windows 用 `windows`）+ 字体文件回退注册 + 拿不到 CJK 字体则显式报错退出。实测密度 `main_zh` 0.0115 → **0.0470**，目视文字全部可读。

**教训**：**"去更好的环境重跑"这类结论，如果没定位到机制，可能只是把问题搬了个地方。** 判断标准是：能不能解释"为什么在这个环境会坏"。

### #11 → #12/#15：一个工具发现了两个，另一个工具发现了两个

**#11（预设静默覆盖用户设置）**：新写的"空转检查"工具（`noop_probe.py`）**第一次运行就发现** —— 关掉凝并开关后终态**完全不变**。这就证明：这个开关根本没起作用。顺着查发现是"案例预设"在运行前把用户改的值覆盖回去了。

修复思路很关键：把预设从"强制值"改成"**建议值**"（用户显式改过的键不再被覆盖），并引入 `explicit_keys` 记录"用户动过哪些"。

**#12（RDB 核心模式死控件）/ #15（`mapping_scheme` 死配置）**：靠"契约体检"（`config_roundtrip.py`）发现 —— 它**自动比对"界面送出的环境变量" vs "核心读取的环境变量"**，差集就是死控件。一次跑出两条。

**这两个案例的价值**：把"发现"从"靠人读代码"变成"靠工具对账"。**能在一条命令里列出来的问题，就不该留给三个月后的人去翻代码。**

### #24 越界值让核心死循环：从代码推断到实测确认

**怎么发现的**：审阅界面控件范围时注意到，方法类控件都是 0–9 的数字框，而核心只认少数几个值。于是去读核心的分发逻辑（`ModuleAdaptstep.f90:86-100`）：

```fortran
elseif (solver.eq.0) then      ! euler
elseif (solver.eq.1) then      ! ETR
elseif (solver.eq.2) then      ! ROS2
endif                          ! ← 没有 else
```

再查"谁推进时间"：唯一推进子步时钟的语句 `current_sub_time = current_sub_time + sub_timestep_splitting` **只存在于三个求解器内部**，而外层是 `do while (...)` 且**没有 exit**。

⇒ **推断**：越界值 ⇒ 不调用任何求解器 ⇒ 时钟不前进 ⇒ 死循环。

**怎么确认的（关键）**：不满足于推断，做实测 —— 同模板同时长，只改一个值：

| `dynamic_solver` | 结果 |
|---|---|
| 2（合法） | 0.26 秒跑完，日志含 5 条 `Progress` |
| **5（越界）** | **60 秒被强杀（exit 124）**，日志停在 `Calculation in progress...`，**0 条 `Progress`** |

"被强杀 + 日志里一条进度都没有"就是死循环的指纹。

**顺带查清同一批的越界语义**：`redistribution_method` 7–9 命中 `CASE DEFAULT` 只打印提示、**静默不做重分配**；`kind_composition` 2–9 两个分支都不进 ⇒ 数组已分配却**从未赋值**（读未初始化内存）。

### #25 `dtmin` 死标签：第一个由脚本而非人工发现的缺陷

**怎么发现的**：本次新建的"字段登记表对账"脚本（`scripts/check_field_registry.py`）第一次运行就报出来：

```
⚠ dtmin_seconds: 登记表说 core_uses=True，但核心源码里除读取外再无使用
```

核实：`dtmin` 全核心 3 处命中 —— 一处**注释**、一处**读取**、一处**声明**，**0 处使用**。而且注释里写着"要把新步长限制在 DTMIN 和 DTMAX 之间"，但**它引用的 `time.inc` 在这个仓库根本不存在**，那个钳制也从未写进代码。

⇒ 界面上的「最小时间步」改什么都没用；而且自适应步长实际没有下限保护。

**意义**：这是第一个**不是靠人读代码**发现的"读了不用"类缺陷。同一脚本还自动报出了 `tag_init`（界面上改不了）、`explicit_keys` 被丢弃（#19 的根因）、归档配置不一致（#22）。

## 四、经验与教训

### 关于"怎么找"

1. **判据先行**。写实验之前先写清"什么结果算推翻我的假设"。写不出反证判据的实验不许做 —— 项目早期为此白跑过多轮。
2. **反证判据要先验证可达性**。写 guard 之前先证明"这个条件在该相位可能为真"。条件恒假时，"结果与原件逐位相同"是**必然**，不构成任何证据（#7 的 v1/v2/v3 就是这么白跑的三轮）。
3. **"改了没变化"是信息，不是失败**。它排除掉一个假设。
4. **用直接仪器，别靠终态推断**。判断"凝并有没有发生"，读核心自己打印的 `Nub Coag` 计数，比比较终态数值可靠得多。
5. **选实验臂要确认"判据量本身非零"**。我曾在"外混臂"上测"凝并是否生效"，而那一臂的粒子数本来就是 0 —— 两臂都 0，什么也证明不了（本轮踩过）。
6. **控制变量要真的控制住**。我用模板做"开/关凝并"对照时，模板自带的案例预设把我的开关**静默改回去了** —— 两臂当然相同。这正是本项目 #19 的现场复现（本轮踩过）。**做对照实验前必须清空一切会覆盖参数的机制。**
7. **先分清"谁的错"**。判断一个缺陷是移植引入还是本体固有，最硬的判据只有一条：**拿原版程序跑同一份配置**。（#7、#18 都是这么定的性。）
8. **手段越自动、越穷举，收获越大**。空转检查、契约体检、字段对账三样工具合计抓到 10 条以上缺陷，且都不需要人猜。

### 关于"怎么确认"

9. **结论三分类**，否则满屏假警报：
   - **致命**（Fortran `STOP` / 信号 / NaN）→ 判 `failed`
   - **浮点标志**（`IEEE_*`，程序继续跑）→ 只报信号，不算失败
   - **信息性打印**（交付**之前**的中间量不守恒）→ 不算信号
   把第二、三类当失败证据，会得出完全相反的结论（#7 的 9.77e-6 就是这么被误读的）。
10. **浮点 / NaN / 非守恒类问题，必须先拿到"文件:行号"再谈补丁**。办法：复制源码树到临时目录 → 在 `SConstruct` 的 debug flags 加 `-ffpe-trap=zero,invalid,overflow -fbacktrace` → 重新编译 → 用变异 exe 跑一臂。`run.log` 会直接给出第一个异常的 `文件:行` + 调用栈。
11. **改了的代码不等于生效的代码**。`.f90` 是图纸，`exe` 是成品，**是两个独立文件**。#9 的修复 2026-09-11 就进了源码树，但 Windows 的 exe 是 2026-05-15 构建的 ⇒ **用户手里那个崩溃一直存在**。这是本项目最贵的一课。改完源码必须：重编译 → 覆盖成品 → **删掉用户目录里的暂存副本**（否则程序还在解析旧 exe）→ 跑标准测试。
12. **止损**。同一个问题连续 2 轮没有新证据/新行号，换方法或标"阻塞-需人工"；禁止连续 3 轮做同一类修补尝试。

### 关于"怎么记"

13. **给缺陷贴对标签**。`port` / `upstream-defect` / `undefined-domain` / `by-design` 四类，决定了"该不该改代码"。混在一起会导致：本该修的（#9）被当"上游固有"放过，本该忽略的（#2/#13）被当"必修"反复啃。
14. **区分"现象成立"和"是缺陷"**。零质量下"凝并一次都没发生"是可复现的事实；但"这算不算缺陷"取决于"零质量输入是否合法"——后者要问模型作者。**不要把不可判定的事写进缺陷结论。**
15. **能改的必须真生效；不能生效的不该出现在界面上。** 静默失真比"不能改"更糟 —— 用户以为改了，拿着错误结论去做实验报告，而且完全无从察觉。本项目有 4 条死控件（#12/#15/#20/#25）+ 多起静默覆盖。
16. **把散落的字段名集中成数据 + 对账脚本**。字段名在 `app/` 里散落 350 处、平均每个字段 13 处，每加一个字段就要手工对齐 10 个位置 —— 这是"改一处漏三处"的结构性原因。#19/#21/#22/#23 四条往返失真全是这么来的。

### 关于"别骗自己"（工具自身的坑）

17. **工具的错误会污染结论**。本次两个实例：
   - 我写的对账脚本第一版**把"读取那一行"也算成"使用"**，于是误报 `tag_thrm` 有真实使用。修掉排除规则后才正确。
   - 探测脚本用**中文做案例标签**，撞出 #27（核心按 GBK 写 CSV、Python 按 UTF-8 读 ⇒ 崩溃）。⇒ **探测脚本一律用 ASCII 标签**，别把工具自身的问题混进探测结论。
18. **先核对再引用**。台账里的行号、机制描述可能过期或本身是未经验证的推断。本次发现：台账记的行号与当前源码差 2–6 行；#5 的机制描述（"Legacy 会算速率"）实测是**段错误**。**引用前先回源码核一遍。**
19. **诚实记录自己改过判断的地方**。本次就有三处：`tag_thrm` 证据从"1 处"更正为"2 处"；#5 从"照算速率"更正为"段错误"；#26 从"确认缺陷 + 建议固定两臂一致"降级为"现象确认、是否算缺陷待定性"（因为发现"内混时初始外混无意义"）。**留错比改错代价更大。**

## 六、如果重来一次，我会先做这四件事

1. **先建"契约对账"工具，再动手改代码**。它能一次列出所有"界面送了、核心不读"的字段 —— 本项目 4 条死控件里有 4 条都会当场现形。
2. **先建"字段登记表"**。27 个字段散落 350 处是"改一处漏三处"的结构性根源；有了表，往返失真类缺陷（#19/#21/#22/#23）从结构上不会发生。
3. **先确认"改了的代码会不会真的跑起来"**。也就是把"重编译 → 覆盖成品 → 清用户暂存副本 → 跑标准测试"固化成一条脚本，而不是靠人记得住（#9 为此卡了一个月）。
4. **先给缺陷分类再排优先级**。分清 `port` / `upstream-defect` / `undefined-domain` / `by-design` 之后，会发现"必修"的其实只有少数几项，其余要么靠收权限消掉、要么根本不用动 —— 这能把台账从"27 条待办"压成"1 件必修 + 3 个决定"。
