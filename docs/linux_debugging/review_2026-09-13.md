## 一、最重要的更正：Q-27 是误报（结论反转）

前一轮登记「v4 修复后 method=6 外混合数量非守恒（终值 2.9e-4、峰值 0.67）⇒ **v4 未完整守恒数量**，需人工复核」。
**复核判定：不成立，已改判 `clean`，人工复核请求撤销。** 依据四条：

1. **打印点归属。** `1-N_new/N_old` 在上游 `euler_coupled.f90` 有**两个**打印点：交付给邻居**之前**的 `:373`（上游该处 `:377` 写的就是 `!STOP`——作者视为非致命），与**之后**的 `:424/:428`（**活 STOP**）。两者字面相同、语义相反。
2. **日志归因。** `q17_boundary` 跑满 512 步，该值共 3,395 条，**全部**紧跟 `INFO redistribution: nombre retenu avant livraison aux voisins`（"交付给邻居之前保留的数量"）；而交付后的 `non conservation du nombre total !!` 出现 **0 次**（stock 同 cfg 出现 8 次并 STOP）。
3. **代数上该量按构造非零。** `AN/BN + CN/DN ≡ 1` ⇒ `N_1`（本 bin 留存）与 `N_2`（交付邻居）互补；交付前只累加 `N_1`，故该值恒等于**本次调用的 hand-out 比例**，不是守恒残差。
4. **结论：v4 修复后数量守恒**，不存在待解释的残差。

连带更正（原记录里的三处数字问题）：

- 「修后 9.77e-6 / 修前 5.4168e-4，降 55 倍」**不成立**：两个数同出 `bug7_fpetrap5`（其源码树 `/tmp/bug7_fpetrap/scram` 已含 v4 主体 ⇒ 修复后构建）的**同一判据点、两个不同子群体**（`N_ancien` 3.21e9 与 1.88e7）。该 run 打完这两条消息后仍跑到 `Progress: 100%` 并写出终态表，反证它们只能出自 `!STOP` 那处。
- 「峰值 0.67」：实测全日志最大 `|1-N_new/N_old| = 0.877`（step 0）。
- 「全程残差增长」：与自身数据矛盾（中途 0.67 > 终值 2.9e-4）。
- 「数量非守恒属上游设计（凝并减粒子数）」：归因不对口——凝并在 coagulation 模块，与本处重分配中间量无关。

**影响**：Q-27 无需人工复核；`proposals/bug7_double_add_v4.patch` **仍然有效**，按原流程由人工/Windows 侧落盘（见 Windows 规划 W2）。

## 三、工具修正：`scripts/linux/probe_cell.py` 致命关键字判据

旧写法 `LOG_FATAL_PATTERNS = ["non conservation", "STOP", …]` 有两类误判，会让**任何走 `euler_coupled` 的格子恒判 failed**：

- 上游 `:248/:259` 的逐 bin 信息性打印 `non conservation de la masse/nombre ds algo!!`（该处**没有** STOP）被裸 `"non conservation"` 命中；
- 信息性文本 `sans STOP`（法语"不带 STOP"）被裸 `"STOP"` 命中——这正是上一轮 `status=failed` 的来源。

改为只认交付后的 `:424/:433` 两处 `…total !!`（其后 `:429/:438` 是活 STOP），并把 `sans STOP` 字面量在匹配前摘除。
**验证**：v4 日志 → `fatal=[]`；stock 日志 → `fatal=['non conservation du nombre total']`（正确命中真 Bug #7）。
