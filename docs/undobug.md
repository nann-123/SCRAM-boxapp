## 2. 逐条详述

### U-01 `#23` 载入配置后「混合假设」恒为 `EXTERNAL_MIXING`
- **归类**：`port-defect`（移植层未复刻"从 cfg 反推"的语义）· 配置/界面
- **现象**：载入任何配置文件（含本该是内混的 `n_frac=1` 配置），界面都按"外混"运行；下拉锁死且手改会被弹回；
  提示文字声称"由配置文件决定，不可手动修改"，但**没有任何代码从文件反推**。
- **触发条件**：任何一次"载入配置 → 运行"。
- **原因**：`app/config_binding/config_model.py:101` 把 `mixing_assumption` 写死为 `EXTERNAL_MIXING`；判据缺失（未用 `n_frac==1` 等）。
- **实测证据**（2026-09-29，判据 R-01）：`n_frac=1` → `EXTERNAL_MIXING`，`n_frac=3` → `EXTERNAL_MIXING`。
- **处置选项**：a 按 `n_frac` 反推（推荐）／b 放开手选／c 维持现状但把提示文字改成"不由 cfg 决定"。
- **复核补充（2026-09-29 复核乙）**：三件套齐 —— ① 解析层写死 `config_model.py:101`；② 锁定值来源 `main_window.py:656`（`self._mixing_scheme_locked` ← `data["mixing_assumption"]`）；
  ③ 手改被弹回 `main_window.py:991-994`；④ 提示文字 `app/i18n/zh_CN.json:15`「混合假设由载入的配置文件决定，不可手动修改」。全仓无按 `n_frac` 反推的代码。
- **复核补充 · 与比较运行无关（实测）**：比较模式的两条腿写死 `("INTERNAL_MIXING","EXTERNAL_MIXING")`（`main_window.py:1114`），**不读下拉** ⇒
  这把锁只影响"单跑"；比较运行永远跑内/外两臂，不受锁定影响。
- **复核补充 · 锁的由来**：当初做成"静默弹回"，是因为预览框画不出改写结果（见 **U-18**）—— 修好 U-18 后本条的选项 b 才有意义。
- **复核**：`check_remaining_items.py` 的 R-01 由 FAIL 翻 PASS；对 `gmd_paris_full` 的既有结果应逐位不变。

### U-02 `#15` 配置标量 `mapping_scheme` 从不进入核心
- **归类**：`port-defect`·配置
- **现象**：配置里 `mapping_scheme`（`LEGACY` / `DETERMINISTIC_NEAREST`）不产生任何效果；`run.log` 里 `mapping_mode` 恒为固定值。
- **触发条件**：任何配置（无论是模板还是手工 cfg）。
- **原因**：`run_service.py:123` 送的是 `self._coag_mapping_mode(scheme)`，而那个 `scheme` 是**混合假设**（`INTERNAL_MIXING`/`EXTERNAL_MIXING`），
  两者都不等于 `LEGACY` ⇒ 恒返回 `COAG_TARGET_NEAREST`；且 `_with_mixing_assumption`（`:343`）还把 `mapping_scheme` 强写成 `DETERMINISTIC_NEAREST`。
- **实测证据**（判据 R-02）：`mapping_scheme=LEGACY` → env 仍是 `COAG_TARGET_NEAREST`；
  内核其实已支持 `LEGACY`/`COAG_TARGET_NEAREST`/`WEIGHTED_CURRENT`/`WEIGHTED_SOFT`/`LCP`（`ModuleCoeffRepartitionBoxmodel.f90:330-350`）。
- **处置选项**：A 把 cfg 的 `mapping_scheme` 接进 `SCRAM_COEFF_REPARTITION_MODE`（**纯 py，无需改内核**）／B 从配置与校验器里移除该字段。
- **复核补充（2026-09-29 复核乙）**：**双重写死** —— 除 `run_service.py:343` 外，界面侧 `main_window.py:699` 也写了一次
  `data["mapping_scheme"] = "DETERMINISTIC_NEAREST"` ⇒ 无论从哪条路径进来，cfg 里的该字段都会被覆盖。
  内核侧取值表已逐条核对（`coeff_parse_repartition_mode`）：接受 `LEGACY` / `NEAREST`/`DETERMINISTIC_NEAREST`/…/`COAG_TARGET_NEAREST` /
  `WEIGHTED_*` / `LCP`，未知值 `error stop` ⇒ 修法 A 成立。
- **复核**：R-02 翻 PASS；`LEGACY` 与 `NEAREST` 两臂应给出不同终态（若仍相同，说明该开关在该配置下不敏感，需另记）。

### U-03 `#16` 界面「环境状态」三选项在出厂配置下无任何数值效果
- **归类**：`port-defect`·界面
- **现象**：霾天 / 城市 / 清洁三选项结果**逐位相同**（`gmd_paris_full` 下 t=0 质量 `21.583170063260344`、数量 `1.4625e10` 三选一都一样）。
- **触发条件**：出厂模板（`tag_init=1`）下选择任一场景。
- **原因**：是否采用内置三套场景分布由 `tag_init` 决定，而所有基座 cfg 都是 `tag_init=1`，**且 `tag_init` 在界面上没有暴露**。
  已证：`tag_init=0` 时三场景确实产生不同结果（终态质量 EXT `11.1139/11.1076/11.1028`）。
- **实测证据**（判据 R-06）：选「城市」后 `tag_init` 仍 = 1。
- **处置选项**：a 场景与 `tag_init` 联动（推荐 A′：非论文验证模式时联动）／b 暴露 `tag_init` 并标注条件／c 移除下拉。

## 6. 附：nl5 模式“没有数量”问题的来龙去脉与现状（2026-09-30 复核）

**问题**：nl5（论文验证模式）的 cfg **按设计不含**逐档初始粒子数那三行（内核该模式自足硬编码，读了也不用；
写入器同步省略，见 `config_model._has_emission_block`）。但内核有一段"整档搬列"代码（块 ④）会读
`init_bin_number`，而该数组在 nl5 下**从未被赋值** ⇒ 粒子数取未定义值（带体检的构建报异常格停机、
不带的静默继续）。出厂雾霾模板（nl5 + `tag_external=0` + `N_frac>1` + `Tag_init=1`）正是这一种。

**解决（`ce0a197`，2026-09-29，已随 1.2 重建）**：
1. **块 ④ 加进入条件**：`if(tag_external.eq.0.and.N_frac.gt.1)` → 追加 `.and.nucl_model.ne.5.and.Tag_init.eq.1`，
   nl5 直接跳过该段（初值已由 nl5 分支按列摆好）；
2. **兜底清零**：`init_bin_mass`、`init_bin_number` 分配后显式 `=0.d0`，让残余误读得到确定的 0 而非垃圾；
3. 数量从哪来：nl5 用内置霾天分布算 `mass_init`/`number_init`（`dist_init_mass_number`），
   内混写 `number_init(j)`（单列全量），外混各写 `number_init(k)/2`（纯 SO4 列 + 纯 BC 列，合计等于单列）。

**现在匹配吗（2026-09-30 实测，当前 1.2 Windows 核）**：两臂初始状态**逐位一致** ——
初始总质量 `37.679073599845388`、初始粒子数分布 `10232917661.8465`、逐格初值质量数组 `68.184033`。
修复前外混臂的质量是内混的 6 倍（`226.07444159907240`）、粒子数为未定义值；现均已消除。
