## 0. 一句话看懂

这个软件有三层开关：**配置文件（点菜单）→ 界面（用户点）→ 环境变量（界面偷偷塞的便条）**。
核心程序只认"点菜单"里它认识的那些项，以及少数几张便条。

**全部的"死开关"问题都是同一句话：菜单上写了，厨房不认。**

数量速览：

| 层 | 数量 | 说明 |
|---|---|---|
| 配置文件标量开关/标签 | **27 个** | 核心按固定顺序逐行读 |
| 配置文件表格块 | **6 张** | 物种表、初始数浓度、2 行排放、粒径边界、质量分数边界 |
| 界面勾选框 | 4 个 | 凝并 / 冷凝 / 成核 / 初始外混放置 |
| 界面下拉框 | 8 个 | 混合假设、案例预设、模板、环境状态、密度模式、RDB 选项、界面模式、语言 |
| 界面数字框 | 15 个 | 温压湿、时长、步长、各种方法号与分段数 |
| 环境变量（界面注入） | **8 个** | 其中核心只读 **6 个**，另 2 个是死的 |
| 核心实际读取的标签 | 25 个 | 见附录 A |
| **已确认的死开关 / 死配置** | **3 个 + 1 个门控** | Bug #12、#15、#16，以及 `cut_dim` 的注释错位 |

## 1. 配置文件里的 27 个开关：按"你到底关心什么"分五组

配置文件就是纯文本 `.cfg`，一行一个设置。核心程序从头往下逐行读，**行的顺序不能变**。

### 第 1 组：物理过程开关（决定"这次算什么"）— 5 个

| 名字 | 人话 | 界面能改吗 |
|---|---|---|
| `with_coag` | 算不算凝并（粒子撞在一起） | ✅ 勾选框 |
| `with_cond` | 算不算冷凝/蒸发（气体变成液体包在粒子上） | ✅ 勾选框 |
| `with_nucl` | 算不算成核（气体自己凝出新的小粒子） | ✅ 勾选框 |
| `tag_external` | 初始粒子按"外混"摆还是按"内混"摆 | ✅ 勾选框 |
| `tagrho` | 密度用真实值（按组分算）还是固定值 | ✅ 下拉框 |

### 第 2 组：数值方法开关（决定"用哪个算法"）— 9 个

这一组是"专家旋钮"，界面上只有切到「高级模式」才看得见。

| 名字 | 人话 | 取值 |
|---|---|---|
| `nucl_model` | 用哪套成核公式 | 1 = 硫酸-氨-水三元成核；5 = 论文验证专用硬编码模式 |
| `sulfate_computation` | 硫酸盐怎么算 | 0 = 普通 / 1 = 显式 |
| `dynamic_solver` | 时间积分用哪个解法 | 0 = euler / 1 = ETR / 2 = ROS2 |
| `tag_thrm` | 热力学用哪套 | 0 = 只算水 / 1 = isorropia 完整无机气溶胶 |
| `redistribution_method` | 重新分配用哪个方法（**1.2 语义，2026-09-20 更正**） | **1 = 不做尺寸重分配**（`ProgramSCRAM.f90:139` 是 `if(method.ge.2)`，所以 0/1 直接跳过尺寸重分布，只做组成重分配）；**≥2 默认一律走 1.2 新内核 `redistribution_size12()`**（moving-center dual-pivot），旧编号含义被覆盖 ⇒ 2/3/4/5/6 在默认下**等价、逐位相同**；只有设 `SCRAM_REDISTRIBUTION_MODE=legacy` 才恢复旧语义：2 = 移动直径 / 3 = euler_mass / 4 = euler_number / 5 = hemen / 6 = euler_coupled |
| `redistribution_option` | RDB 核心模式 | legacy / core_conserv / core_nogrow / core_smallgrow ⚠️ **死开关，见 §5** |
| `kind_grid` | 粒径网格怎么定 | 0 = 自动生成 / 其他 = 手动给边界 |
| `kind_composition` | 组成怎么离散 | 0 = 默认 |
| `cut_dim` | 切割粒径 | ⚠️ 注释写的是 `Tag_eqilibirum`，实际是另一个东西，见 §5 |

### 第 3 组：环境与初值 — 5 个

`init_scenario`（1 霾天 / 2 城市 / 3 清洁，⚠️ **被门控，见 §5**）、`temperature`（K）、`pressure`（Pa）、`humidity`（0–1）、`fixed_density`（kg/m³）。

### 第 4 组：规模 — 4 个（决定表格多大）

| 名字 | 人话 | 注意 |
|---|---|---|
| `n_species` | 多少种化学组分 | 改它 ⇒ 物种表行数变 |
| `n_sizebin` | 粒径分多少段 | 改它 ⇒ 粒径边界重算，**手动调过的边界会丢** |
| `n_frac` | 质量分数分多少段 | 只有外混用；改它 ⇒ 分数边界重算 |
| `n_groups` | 分几组 | 组内按内混、组间按外混 |

### 第 5 组：运行与文件 — 3 个

`final_time_hours`（模拟多久）、`dtmin_seconds`（最小时间步）、`coefficient_file`（系数文件，⚠️ **界面上有控件但被隐藏**，只能靠载入 cfg 带入）。

### 另有一个"隐形"开关

| 名字 | 说明 |
|---|---|
| **`tag_init`** | 决定"初始质量怎么给"：0 = 用内置的三套场景分布自动算；1 = 用配置文件里逐档写好的质量。**这是 27 个里唯一一个界面上完全没有的**。出厂的所有模板都是 1。它正是「环境状态」失效的原因（§5）。 |

### 6 张表格块

`species_records`（每物种一行）、`init_bin_number`（各粒径段初始粒子数）、`init_bin_emission_species_1/2`（前两个物种的排放）、`diameter_bounds`（粒径边界，长度 = n_sizebin+1）、`fraction_bounds`（质量分数边界，长度 = n_frac+1）。

## 2. 界面上的开关（用户实际看到的）

界面对应 7 个标签页：实验设置 / 结构编辑 / 运行监控 / 结果分析 / 报告导出 / 设置 / 帮助。

**实验设置页**（主战场）：

- 4 个勾选框：启用凝并、启用冷凝/蒸发、启用成核、初始粒子按外混放置
- 8 个下拉框：混合假设（**只读锁死**）、案例预设（11 个）、模板（7 个）、环境状态（霾天/城市/清洁）、密度模式、RDB 核心模式、界面模式（基础/高级）、界面语言
- 15 个数字框：温度、压力、湿度、固定密度、模拟时长、最小时间步，加上高级模式下的成核模型/硫酸冷凝模式/RDB 数值方法/动力学求解器/热力学标记/网格模式/组分离散模式/切分粒径/组分组数
- 3 个文本框：实验名称、输出目录、系数文件（隐藏）
- 4 个按钮：载入配置 / 保存配置 / 另存为 / 校验配置

**其它页**：结构编辑页有 3 个数字框（组分数/粒径段数/质量分数段数）+ 3 个按钮（生成结构/重建表格/自动生成对数粒径边界）+ 5 张可编辑表格；运行监控页有 3 个运行按钮 + 17 个实时指标；结果分析页有案例选择 + 4 个按钮；报告页有标题框 + 可勾选的图列表 + 3 个按钮；设置页有语言、输出目录、界面模式。

**联动规则**（改一个，另一个自动消失/出现）：

| 条件 | 效果 |
|---|---|
| 关掉冷凝 | 隐藏"冷凝相关"整张卡 |
| 关掉成核 | 隐藏"成核相关"整张卡 |
| 选内混 | 隐藏"外混相关"卡（组分组数）；显示内混说明 |
| 选外混 | 显示"外混能区分同粒径不同组成"说明 |
| 密度选"真实密度" | 隐藏"固定密度"输入框 |
| 界面模式选"基础" | 隐藏全部 4 张高级卡片 |

## 3. 三层开关是怎么接线的

```
                     ┌──────────────────────────────┐
   界面控件 ────────► │  .cfg 配置文件（26 个标量）    │ ──► Fortran read(10,*) 逐行读
                     └──────────────────────────────┘
                     ┌──────────────────────────────┐
   界面控件 ────────► │  环境变量（8 个）             │ ──► Fortran 只读其中 6 个
                     └──────────────────────────────┘
```

**环境变量这层的实情**：

| 变量 | 谁在用 |
|---|---|
| `SCRAM_RESULTS_DIR` | ✅ 核心读 |
| `SCRAM_TESTCASE` | ✅ 核心读 |
| `SCRAM_PROCESS_COMBO` | ✅ 核心读 |
| `SCRAM_SCHEME_NAME` | ✅ 核心读 |

## 4. 为什么会有死开关？四个真实原因

### 原因一：界面是"后来套上去的壳"，核心根本不认识壳发明的新概念 ★最主要

原始 SCRAM 是 2015 年论文（Zhu et al. 2015）配套的研究代码，**输入方式只有配置文件一种**。
现在这个图形界面是后来加的壳。壳的设计者按自己的想法发明了一个新选项——
"RDB 核心模式"，给了它 4 个值（legacy / core_conserv / core_nogrow / core_smallgrow），
还写了中文标签、下拉框、说明文档。

但核心程序里**从来没有实现过这个概念**。壳只好把这个值塞进环境变量，指望核心自己去读。
而核心只读它自己认识的那几个环境变量，压根没看过这两个。

于是：**壳改了、菜单上多了一道菜、厨房压根没这道菜的灶。**

**证据**：`grep -rn RDB_CORE_CONSERV SRC/` → 零匹配；四个值跑出来的终态**逐位完全相同**（连小数点后 15 位都一样）。这就是 Bug #12。

### 原因二：两个东西重名，接线接错了

配置文件里确实有一个叫 `mapping_scheme` 的开关（可选 `LEGACY` / `DETERMINISTIC_NEAREST`），
模板和校验器都在用它。界面上也有一个中文叫「混合假设」的下拉框，代码里变量名也叫 `mapping_scheme`。

**但这两个不是一回事**：

- 配置文件里的 `mapping_scheme` = "凝并系数用不用查表"
- 界面下拉框绑的 = "内混还是外混"

结果送进核心的是"内混/外混"这个值，而核心的判断是 `if scheme == "LEGACY"`——
这个条件**永远为假**，所以核心永远按 `COAG_TARGET_NEAREST` 跑。这就是 Bug #15。

**教训**：同名不同物，是接口类缺陷最容易踩的坑。

### 原因三：开关是好的，但被另一个"藏起来的开关"挡住了（门控）

界面上的「环境状态」有霾天 / 城市 / 清洁三选一。用户选了半天，结果**一模一样**。

原因不是这个功能坏了：要不要用这三套内置场景分布，是由 `tag_init` 决定的——
而 `tag_init` 界面上**根本没有**，用户改不了，出厂模板全是 1（=不用场景分布，用配置里的数）。

实测把它设成 0，三个场景确实产生不同结果。**功能是好的，只是被挡住了。** 这就是 Bug #16。

### 原因四：上游代码自己的注释和代码对不上

配置文件第 16 行的原始注释写的是 `##Tag_eqilibirum`（平衡标记），
但核心实际把这行读进了 `Cut_dim`（切割粒径）；而 `Tag_equi` 这个变量在核心源码里
**声明了、却从头到尾没用过一次**。

这是 2015 年那份代码自己遗留的问题，不是界面壳的错。看配置文件注释时要知道这件事。

## 6. "是不是原先代码就有问题？"——必须分两类看

这是整个项目最重要的一个判断。`docs/BUG_TRACKING.md` 用三个标签严格区分：

| 标签 | 含义 | 典型条目 | 该不该修 |
|---|---|---|---|
| **`port`**（移植层） | **后来加的界面/包装层**写错了 | #11 预设覆盖用户设置、#12 死控件、#15 死配置、#16 门控、#9 文件指针 | ✅ 该修，算发布闸门 |
| **`upstream`**（本体固有） | **2015 年那份研究代码本来就这样** | #7 重分配不守恒、#2/#5 零质量行为不一致、#14 方法 3/5 粒子数暴增、#17 排放窗口仅 44 分钟 | ❌ 只登记，**不算发布闸门** |
| **`needs-domain`** | 需要懂物理的人拍板 | #13 零质量下内外混粒子数差 4 个数量级 | ⏸️ 待人工定性 |

**关键事实**：移植过来的核心数值代码与原始研究版本**基本逐字节一致**
（`euler_coupled` / `redist_euler` / `euler_mass` / `hemen` / `ModuleThermodynamics` / `isorropia` 全部一致）。

所以可以说得很干脆：

> **核心本身的老毛病（数量不守恒、零质量怪异、排放窗口写死）= 原作者的代码就是这样，不是移植搞坏的，一般不改。**
> **所有"死开关/死配置"= 后加的界面壳写错了，是移植层的问题，该修。**

两条线索不要混：一个是"模型算得对不对"，一个是"界面和核心有没有接上"。这个项目里，
**前者大多不用管，后者才是主战场**。

## 8. 怎么调试——这个项目已经有一套成熟方法

> **2026-09-20 补注**：本节原先引用的 Linux 自动化排查工具链（`scripts/linux/` 下的
> `config_roundtrip.py`、`noop_probe.py`、`probe_cell.py`、`probe_suggest.py`、
> `template_audit.py` 等），以及夹具目录 `docs/checktest/` 与补丁目录 `proposals/`，
> **已随移植缺陷收口一并移除**。下面的**方法与判据仍然有效**，只是脚本不再随仓库分发，
> 需要时可从 git 历史找回。现役工具只剩 `scripts/linux/build_runtime.sh`（构建 Linux 内核）
> 与 `scripts/run_standard_tests.py`（标准测试）。

### 8.1 曾经的四把探针（按性价比排序）

| 探针 | 命令 | 一句话作用 |
|---|---|---|
| **契约体检** ★首选 | `python scripts/linux/config_roundtrip.py` | **一次列出所有死开关**：自动比对"界面送出的环境变量" vs "核心读取的环境变量"（差集就是死控件）、"cfg 读序" vs "本体读序"、"界面字段" vs "cfg 写出" |
| **空转检测** | `python scripts/linux/noop_probe.py --template <模板>` | 判据是"关掉开关后终态必须变"；不变 ⇒ 该路径根本没生效（#2/#5/#16 那一类） |
| **单格控制变量** | `python scripts/linux/probe_cell.py --template <模板> --set 字段=值` | 只改一个字段跑一臂，和默认臂比终态 |
| **夹具复跑** | `python scripts/linux/probe_cell.py --cfg docs/checktest/<夹具>.cfg` | 按文件里写死的值跑，不套预设（夹具惯例：`*_test.cfg` 复现 + `*_fixed.cfg` 对照） |
| **模板体检** | `python scripts/linux/template_audit.py` | 7 个模板逐个断言"开了的过程必须真起作用"（如 `with_cond=1` ⇒ `Mass Cond>0`） |

### 8.2 你自己查"某个开关到底有没有用"的最短路径

1. **核心读不读它？** 打开 `SRC/ModuleDiscretization.f90`，看第 84–105 行那份 `read(10,*)` 清单里有没有这个名字。
2. **不走 cfg 就走环境变量？** `grep -rn "SCRAM_" SRC/` 看核心读了哪些环境变量。
3. **两者都不读 ⇒ 死开关**，结案。
4. **核心读了但结果一样？** 做两臂对照（只改一个字段、其余全同），比终态数值是否逐位相同。
   原先用 `probe_cell --set 字段=值`；现在写个最小脚本调 `RunService.run_comparison` 即可。
5. **想一次列全？** 原先 `config_roundtrip.py` 一条命令就能列出所有死开关——它比对
   "界面送出的环境变量" vs "核心读取的环境变量" 的差集（#12/#15 就是这么定性的），
   外加 cfg 读序与 GUI 字段两项。脚本已移除，判据可直接照做：
   `app/services/run_service.py` 里的 `SCRAM_*` 集合 vs `SRC/*.f90` 里的
   `get_environment_variable` 集合，差集即死控件。

### 8.3 定位浮点类问题：先拿到"文件:行号"，再谈补丁 ★铁律

浮点异常 / NaN / 数量不守恒这类问题，**必须先定位到具体行**，禁止凭猜写补丁。

```bash
# ① 复制源码树到临时目录（绝不动仓库运行时）
cp -a core/executables_or_wrappers/runtime/windows/source/SCRAM1.2 /tmp/<tag>/scram

# ② 在副本的 SConstruct 的 debug_flags 里加浮点陷阱
#    -ffpe-trap=zero,invalid,overflow -fbacktrace
cd /tmp/<tag>/scram && FC=gfortran CC=gcc scons mode=debug

# ③ 用变异 exe 跑一臂 → run.log 直接给出第一个异常的文件:行号 + 调用栈
#    run_service 会优先采用 SCRAM_PROGRAMSCRAM 指定的可执行文件
#    （原先的 probe_cell.py 已随工具链移除；现在直接用 RunService 跑一臂即可）
export SCRAM_PROGRAMSCRAM=/tmp/<tag>/scram/ProgramSCRAM
```

**反面教材（Bug #7）**：v1 / v2 / v3 三个补丁全打在"几何分母为零"上，白跑三轮，
最后发现 guard 条件在本相位**恒为假**——变异结果与原件逐位相同是必然的，压根不构成反证。
一次陷阱构建就把真凶定位到了 `log10(0)` 和"hand-out 重复交付"。

### 8.4 写 guard 之前，先证明这个条件可能为真

如果条件恒假（例：某相位 `kloc(k) ≡ 1`，而 guard 要求 `kloc(k) > 1`），
"改了没变化"是必然而非证据。补丁提案里必须写明**条件可达性**。

### 8.5 结论三分类（不然会满屏假警报）

| 类别 | 例子 | 判为 |
|---|---|---|
| 致命 | Fortran `STOP`、收到信号、NaN | `failed` |
| 浮点标志 | `IEEE_DIVIDE_BY_ZERO` 等，程序继续跑 | 只报信号，不算失败 |
| 信息性打印 | 交付**之前**的中间量不守恒 | 不算信号 |

`run_service` 已按这套分类实现（口径原先与已移除的 `probe_cell.py` 共用），不要拿 `IEEE_*` 标志当失败证据。

### 8.6 止损与反停滞

- 同一个 Bug **连续 2 轮**没有新证据/新行号 ⇒ 换方法，或标"阻塞-需人工"
- 禁止连续 3 轮做同一类补丁尝试
- 连续 3 轮无新发现 ⇒ 升级探测层：覆盖矩阵 → 已知 Bug 变体 → 源码线索（`STOP`、`nucl_model` 分支、无保护除法）→ 失败反推
- 四层都无可做 ⇒ 写明"探测饱和"，转入发布闸门，不许继续空跑

### 8.7 改动纪律

| 范围 | 允许 |
|---|---|
| 配置/契约层（`app/services/**`、`app/config_binding/**`、`core/templates/**`、`core/defaults/**`） | ✅ 可自主修，但每笔必须交"三件套"：改前改后数值对比 + 体检脚本输出 + 是否改变基线的声明 |
| 核心算法（`SRC/*.f90`） | ⚠️ 改动需人工拍板；提案须写清补丁内容、条件可达性与验证判据 |

| `core/executables_or_wrappers/runtime/windows/**`、两个 Windows 打包脚本 | 🚫 禁改。原先由 `check_windows_parity.sh` 判硬失败，该守卫已于 2026-09-20 移除，现靠人工遵守 |
